Also, because the auto group is an `h3` inside the `MIDI dosyaları` `h2` and sits after the manual upload form, it reads as part of the manual group, which works against D116. Fix: render the automatic group (status, draft, published file) first, straight under `Nota ve otomatik MIDI`, either by moving the `{(auto || draft || job) && …}` block above the manual list in `MidiEditor`, or by making it its own `h2` section rendered between `ScoreEditor` and `MidiEditor` on `duzenle/page.tsx`. Then give the manual list its own `MIDI` sub-heading so both groups have a heading (AC 33: "the editor shows the same two groups").
2. **The convert form stays live while a job is queued or running** (`score-editor.tsx:262-268`; the `active` prop is already passed in). Pressing `MIDI'ye çevir` again only produces the `Bu eserde zaten bir çeviri sürüyor.` toast. A non-technical user will press it again when nothing seems to happen (see P2-1). Fix: when `active`, don't render `ConvertForm`, or render it with a disabled fieldset and the button text `Çeviri sürüyor…`. Also disable `Değiştir`/`Sil` with the same reason shown inline (`score-editor.tsx:237-255`; today `Değiştir` shows a toast and `Sil` opens the confirm, then fails on the server).
3. **`Taslak hazır` stays on screen after the draft is gone** (`midi-editor.tsx:281`, `omr-status.tsx:59-66`). The latest job stays `succeeded` after a manager publishes or deletes the draft, so the status card keeps saying `Taslak hazır` next to no draft, or right above the already-published file. Fix: in `MidiEditor`, render `OmrStatus` for `succeeded` only while `draft` exists, or pass `job` only when `job.state !== "succeeded" || draft`. Queued, running and failed stay as they are.
4. **The wake lock holds the screen on for as long as the panel is open, even when paused or finished** (`src/components/midi/midi-player.tsx:250-283`). A singer who pauses, or lets the piece end, and puts the phone down with the piece page open gets a screen that never sleeps, which drains the battery. Fix: make the effect depend on `state === "playing"`: request on play, and release on pause, on `ended` and on unmount. Keep the re-request on `visible` only while playing. The comment's intent ("audio stops when the phone locks") only needs the lock while sound is playing.
5. **Publishing pushes to the whole choir in one tap, with no confirm on the first publish** (`src/components/midi/draft-card.tsx:76`). `Yayınla` sits next to `Sil`, and a mistaken tap is irreversible: every member gets a notification for a draft nobody has listened to. The spec only asks for a confirm when replacing an existing file, so this is a counter-proposal for the PO: always confirm, with title `Yayınlansın mı?` and description `Koristler hemen görür ve bildirim alır.` (plus the existing replace sentence when `replacesPublished`). If the PO declines, leave it as it is.

## Backend/security review

Reviewer: backend (security + DB). Date: 2026-10-24. Scope: the uncommitted Phase 11 backend: `drizzle/0014_phase11_score_omr.sql`, `src/lib/omr/*`, `src/app/api/omr/*`, `src/app/api/dosya/nota/*`, the draft filter in `src/lib/repertoire-midi.ts`, `src/lib/storage/files.ts`, `src/app/api/dosya/midi/[id]/route.ts` and `src/lib/push/*`, the actions in `src/app/(portal)/repertuvar/omr-actions.ts` / `midi-actions.ts` / `actions.ts`, `.github/workflows/omr.yml`, `omr/portal.py`, `omr/convert.py`.

What I checked and found sound:
- **Migration 0014, rehearsed** on a scratch DB built from 0000–0013 with seeded `midi_files`, `storage_deletions` (pending with attempts/last_error, done) and `storage_events` (null/midi/recording areas, a gap in ids), then 0014 applied through `client.migrate` (one transaction, as drizzle-kit does on Turso). Result: the six pre-existing triggers are byte-identical (the three 0010 queue triggers are recreated; `recordings_audio_final` and the budget triggers are untouched), plus `piece_scores_queue_on_delete`; both tables' indexes are identical; every `storage_deletions` row is identical; `storage_events` rows identical apart from column order (`area` moved before `bytes`, harmless: every insert names its columns, and the dump uses names); `foreign_key_check` empty, `integrity_check` ok; existing MIDI rows read `auto=0, status='published'`; deleting a MIDI row still queues its key; `score` is accepted by both CHECKs. The new CHECKs are supersets of the old ones, so the copy can't fail on live data, and the ADD COLUMN CHECKs pass every existing row (defaults `0`/`published`/NULL). Nothing references `storage_deletions`/`storage_events` by FK, so the `PRAGMA foreign_keys` lines being no-ops inside the batch transaction doesn't matter. A failure mid-file rolls the whole batch back (hrana batch / local `migrate` are transactional), so the trigger drops can't be left half-done.
- **HMAC** (`src/lib/omr/signature.ts`, `machine.ts`): header shape and ±300 s are checked before the body is read (unsigned junk costs nothing), the body is read with a hard cap, the signature covers timestamp, method, path (so it binds the job id and endpoint) and the body hash, the compare is constant-time, and the uuid/DB lookup only happens after the signature, so unsigned callers learn nothing. Replay is closed by the state machine: every write is `... where state in ('queued','running')` / `state = 'queued'` inside a write transaction, and `sonuc` re-checks state in its transaction (a parallel replay ends in `Conflict` with the blob released). The dev secret is refused in production (`config.ts:33`), outbox mode exists only outside production on a local DB, and logs carry only job id/state/kind/status.
- **Score routes**: upload is same-origin + session + manager, rate-limited before reading, refused by declared length and again while streaming (cap 4 MiB, not buffered beyond it), sniffed by bytes, locked while a job is active (checked again inside the transaction), and goes through hold → put → commit with the old key queued by the trigger. Delivery needs an active session, is rate-limited per viewer, counts as `score` transfer (excluded from the recording stop in `quota.ts`), and carries `nosniff`, a sandbox CSP and `private` caching. I loaded a PDF in the e2e Chrome with `sandbox` and with `default-src 'none'; sandbox`: the built-in viewer renders in both.
- **Draft visibility**: every member read goes through `status = 'published'` (`midiForPiece`, `heroMidi`/`homeworkMidi` → home `?cal=1`, piece hero, homework, `midiCount`); the MIDI route answers 404 to non-managers for a draft before touching the rate limit and serves drafts `no-store`; the morning repertoire line excludes `auto = 1`; the only push is on publish. The editor and `omrState` are manager-only.
- **Actions**: every exported action in `omr-actions.ts` starts with `assertManager()` (null → `MSG.forbidden`) and validates ids with zod; publish/delete/score-delete are single conditional statements in a write transaction, so double taps give `Dosya bulunamadı.`; limits are counted in the same transaction as the insert, and the partial unique index catches parallel starts. The manual cap counts `auto = 0` in both places in `uploadMidi`.
- **Workflow**: `workflow_dispatch` only, `contents: read`, inputs reach `run:` only through `env:` and are regex-checked first, `persist-credentials: false`, the Audiveris `.deb` is sha256-checked on every run (also after a cache restore), no artifacts, the secret is only in the env of the `portal.py` steps.
- e2e `phase11-a` (52/52) and `phase11-b` (69/69) pass against the dev server.

### P2

1. **A code rollback after 0014 would show drafts to members.** `README.md:101-102` says Promote-ing the previous deployment is safe because migrations are expand-only. After 0014 that stops being true once a draft exists: the Phase 10 code has no `status` filter (`midiForPiece`/`midiForPart`/`midiForExactPart`, and `/api/dosya/midi/[id]` serves any row), so every draft becomes visible and playable to korists, and the old MIDI route marks it `immutable` for a week. This breaks D103. Fix: add a line to README step 9 (and the §9 go-live checklist): "Before promoting a deployment older than Phase 11, delete undecided drafts: `delete from midi_files where status = 'draft';` (the trigger queues their files)". Optionally make it a script (`npm run omr:drop-drafts`) so nobody has to type SQL against Turso by hand.
2. **The callback secret is in the environment of processes that run third-party code** (`.github/workflows/omr.yml:78-84, 122-131`, `omr/portal.py:83-89, 112`). The `fetch` step runs `portal.py` with `OMR_CALLBACK_SECRET` set and imports `pypdf` to parse the untrusted PDF. The `result`/`fail` steps run setup-python's interpreter, so any `.pth` file installed by `pip install -r omr/requirements.txt` runs with the secret too. The pins have no hashes, and PyPI accepts new wheel files for an already-published version. The steps before them (Audiveris, `convert.py` on OMR output) can also write to that site-packages and to `omr/portal.py`. Anyone holding the secret can forge results and failures and fetch the PDF of any active job. Fix:
   - (a) Split `fetch` into a secret-bearing download that uses only the standard library, and a separate step without the secret: `python omr/pages.py input.pdf` writes `failure.json` with `too_many_pages`/`pdf_unreadable` and `exit 1`.
   - (b) Run every secret-bearing step with the runner's system interpreter in isolated mode, never the setup-python one: `/usr/bin/python3 -I -S omr/portal.py …`.
   - (c) Make it `pip install --require-hashes -r omr/requirements.txt`, with hashes from `pip-compile --generate-hashes` or `pip hash` run locally.
   - (d) Optionally `git checkout -- omr/portal.py`, or compare its sha256 against the commit, before the last two steps.

### P3

1. **No IP rate limit on the unauthenticated machine endpoints** (author flagged; `src/lib/omr/machine.ts:51-62`, `src/proxy.ts:63`). Accepted as is. A request without a well-formed timestamp and signature is refused before the body is read and never touches the DB. A forged-but-well-formed one costs at most a 2 MB read and one SHA-256, still with no DB access. A DB-backed `consumeAttempt` per IP would make every junk request a write, which is worse. Two cheap improvements:
   - Exclude `api/omr/` from the proxy matcher (`src/proxy.ts:63`), like `api/dosya/`. Today the proxy buffers up to 10 MB of every `/api/omr/*` body before the route's cap runs, and adds a nonce/CSP these JSON endpoints don't need.
   - For POST, return 411 when `content-length` is missing.
   If abuse ever shows up in Vercel logs, add a Vercel Firewall rate-limit rule on `/api/omr/` (only if the Hobby plan offers it for free) rather than app code.
2. `src/app/api/dosya/nota/[id]/route.ts:68` overrides `fileHeaders`' `default-src 'none'; sandbox` with plain `sandbox`. Chrome's viewer works with the stricter value (checked), so keep `fileHeaders`' value and update the e2e assertion (`e2e/phase11-a-score.mjs:136`) to accept it. Check Safari/iOS in the go-live step 8 either way.
3. `src/app/api/omr/[id]/sonuc/route.ts:62-82`: a result refused for quota or storage (`503 quota`/`storage`) is retried 3 times by `portal.py` and then reported by the failure step as `output_invalid`. The manager reads "Çeviri sonucu kullanılamadı", but the real cause is the upload pause. Fix: either fail the job in the route with a new portal-side kind (e.g. `storage_full`, which needs a CHECK change, so later), or at least log `{ job, state: "failed", kind: "quota" }` so the cause is visible.
4. `src/lib/omr/midi.ts:13` (`String.fromCharCode(...bytes)`) and `:105` (`Math.max(...scans.map(...))`) spread arrays that a 1 MB file can make large enough to throw `RangeError` → an unhandled 500 (the job still ends `output_invalid` via the workflow's retry + failure step). Signed callers only. Fix: refuse a track-name meta longer than 4 × `OMR_TRACK_NAME_MAX` bytes before decoding, decode Latin-1 with `new TextDecoder("latin1")`, and use a loop for the max.
5. `omr/portal.py:133-142`: the `fail` command only catches `OSError/ValueError/TypeError`. A `failure.json` that is a JSON list (`AttributeError` on `.get`) or holds `Infinity` (`OverflowError` in `int()`) crashes it, so no failure is posted and the job sits until the 45-minute read-time timeout. Fix: `except Exception`, plus `isinstance(data, dict)` and integer checks before using it. Also `request()` (`:52-65`) follows redirects and forwards the `X-Arkhe-*` headers to the new host. Use an opener whose `HTTPRedirectHandler.redirect_request` returns `None`, so a wrong `PORTAL_URL` fails loudly.
6. `.github/workflows/omr.yml:127-128`: `if: failure()` doesn't run when the job hits `timeout-minutes` or is cancelled, so those runs show `timeout` only after 45 minutes. Use `if: failure() || cancelled()`.
7. `.github/workflows/omr.yml:61, 72, 88`: the three action SHAs (`checkout v7.0.1`, `setup-python v7.1.0`, `cache v6.1.0`) couldn't be checked from here (no network in the review sandbox). Before go-live, confirm each SHA is the commit its tag points to on the official `actions/*` repo (GitHub web UI, tag page).
8. `drizzle/0014_phase11_score_omr.sql:98-111`: rebuilding the AUTOINCREMENT `storage_events` resets `sqlite_sequence` to `max(id)` of the surviving rows (the sweep prunes old rows, so ids get reused; in the rehearsal it went 3 → 2). Nothing references these ids, so this is only a note for the Turso rehearsal: don't treat a lower sequence as data loss.
9. `.github/workflows/omr.yml:118`: `ls out/*.mxl | sort | head -n 1` converts only the first movement when Audiveris splits a book (`*.mvt1.mxl`, `*.mvt2.mxl`). Acceptable for this phase. Worth a `no_music`-style kind or a log line when more than one file exists.
