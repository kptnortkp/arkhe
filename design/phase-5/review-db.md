## Findings

### P2 (fix this phase)

- **P2-1 (already fixed while this review was being written)** `openingDate` now lives in `ledger.ts:75`, and `recordDuesPayment` checks it inside the transaction (`aidat/actions.ts:90-95`). The fix is correct. Original finding, kept for the record: **Dues payments skip the opening-date rule (D12).** `src/app/(portal)/finans/aidat/actions.ts:66-109` `recordDuesPayment` never compares `occurredOn` with the opening date. `createEntry` (`checkRefs`, `finans/actions.ts:84`) and the dues branch of `correctEntry` (`:205`) both do. So `Ödeme al` dated before `Ayarlar`'s opening is saved, which breaks the invariant `setOpeningBalances` relies on ("nothing live before the opening"). Fix: move `openingDate(tx)` from `finans/actions.ts:64` into `src/lib/finance/ledger.ts`. Don't export it from the `"use server"` file, or it becomes a callable action. Inside the transaction, after the replay check, return `{ fieldErrors: { occurredOn: ["Tarih açılış bakiyesinden önce olamaz."] } }` when `opened && d.occurredOn < opened`.
- **P2-2 Two finance writes at the same moment: the second one crashes instead of waiting.** I verified this on the copy with `@libsql/client` 0.18. The local `file:` client keeps a connection pool, and a second `transaction("write")` (or an autocommit write) while another connection holds the write lock fails **immediately** with `SQLITE_BUSY` (`busy_timeout` 0). Setting `timeout` doesn't help in-process. The native driver is synchronous, so the waiting `BEGIN IMMEDIATE` blocks the event loop that would have committed the first transaction, and it still fails after the timeout (measured: 2110 ms then BUSY). Money stays correct because nothing is written. But `recordDuesPayment` (`aidat/actions.ts:66`) and the other actions don't catch it, so the second manager gets the error boundary instead of the D17 "sees the new sum" behaviour. That D17 claim came from me, in `db.md` §3, and it's wrong for the local file. Fix (small, in `src/db`): `export async function writeTx<T>(fn)` that runs `db.transaction(fn)` and retries up to ~5 times on `SQLITE_BUSY` (walk `cause`) with an *async* backoff (`await new Promise(r => setTimeout(r, 20 * 2 ** i))`). Use it for every finance `db.transaction` and the single-statement void and meta edits. The retry re-runs the whole closure, so the guard sees the committed sum. Alternative: an in-process promise mutex around write transactions. That works for one Node process only, so I prefer the retry, which also covers Turso lock contention.
- **P2-3 A freeze outlives the payment it protected (D3).** `setDuesRate` (`aidat/actions.ts:399-411`) pins `owed` with a `freeze` row because a payment exists. If that payment is later voided or corrected away, the row stays. `owedFor` (`src/lib/finance/dues.ts:47-52`) keeps charging the old rate on a period with **no** payment, which contradicts D3's "periods with no payment follow the new rate live". Example: korist paid ₺100 for P2, gets switched to İndirimli (freeze ₺300), the ₺100 is voided as a mistake, and korist now owes ₺300 instead of ₺150 with no visible reason. Fix (read-time, no migration): ignore a `freeze` when the live paid sum is 0. Give `owedFor` a `paid` argument (`if (override?.kind === "freeze" && paid === 0) override = null`) and pass it at all four call sites (`queries.ts:596,730`, `ledger.ts:61`; `setDuesRate` passes `null`). The stale row is then harmless, and `setWaiver`'s upsert can still replace it.

### P3 (later)

- **P3-1** `aidat/actions.ts:67-78`, `ledger.ts:11`: the replay ids are `derivedId(clientId, periodId)`, which doesn't include the member. A reused `clientId` for another member on the same period returns `Ödeme alındı: {other name}` and saves nothing. The UI remounts `PaymentForm` per member (`dues-list.tsx:211` `key`), so only a crafted request hits it. Fix: `derivedId(clientId, memberId, periodId)`, or return STALE when `existing` rows have another `member_id`.
- **P3-2** `queries.ts:74,125,453`: `substr(occurred_on,1,7) = ?` (month list, `monthSummary`, `categoryTotals`) can't use `fe_occurred_idx` as a range, so it walks the whole index. Use `occurred_on >= 'YYYY-MM-01' and occurred_on < nextMonth+'-01'` (the year version too). That's harmless at a few thousand rows.
- **P3-3** `queries.ts:216` `Aynı ödemede` filters `payment_group_id` with a full table scan. In the next migration that touches `finance_entries`, add `index("fe_payment_group_idx").on(t.paymentGroupId).where(sql\`payment_group_id is not null\`)`. A plain query can use it, because the predicate implies `is not null`.
- **P3-4** `finans/actions.ts:267-297` `updateEntryMeta` accepts openings (description and document get stamped onto `kind='opening'`) and lets an `income/dues` entry get an `eventId`. The latter pulls dues into that event's P/L as an income line. Fix: refuse `kind === 'opening'` (`OPENING_ONLY_IN_SETTINGS`), and set `withEvent = (income|expense) && category !== 'dues'`.
- **P3-5** `e2e/phase5-finance.mjs:614` hard-codes `18` debtors, against D31 ("never hard-code"). Add `currentDebtors: 18` (and `owingMembers: 19`) to `financeExpected` and assert against those.
- **P3-6** `scripts/finance-fixture.mjs:83-84` only checks `file:`. `seed.ts` also refuses `NODE_ENV=production`, but `e2e/lib.mjs` calls `seedFinance` directly, and it wipes every finance table. If the choir ever self-hosts on a file DB, one stray `npm run e2e` erases the ledger. Add the same `NODE_ENV === "production"` refusal to the fixture.
- **P3-7** `queries.ts:573` (`duesMatrix` roster) and `queries.ts:681` (`myDues`) filter `role in (member, board)`. A payer later made conductor drops out, so `Toplanan` for that period no longer equals the ledger's dues income. Fix: include any user with a live dues row (`or exists (…)`), and let `owesPeriod || paid > 0` decide as it already does per cell.
- **P3-8** `aidat/actions.ts:484-494` `removeWaiver` returns `Muafiyet kaldırıldı.` even when nothing was deleted. Use `.returning()` and send `NOT_FOUND` when it's empty.
- **P3-9** `queries.ts:207-218` `getEntry` runs its three follow-up selects one after another. Use `Promise.all`.
- **P3-10** Phase 1 P2-5 is still open: `busy_timeout` is 0. Given P2-2, *don't* raise `timeout` on the local client. It blocks the event loop. The retry in P2-2 is the fix.
